# 发布说明

正式发布只走 GitHub Actions。`sh/` 下的本地脚本（`deploy.bat` / `deploy.env` / `plink.exe` / `pscp.exe`）
不入库，只给 agent 在本机临时快发用 —— 别把它们当成发布流程的一部分。

## 一、正式发布：GitHub Actions

工作流：`.github/workflows/deploy.yml`

| 触发方式 | 说明 |
|---|---|
| push 到 `github` / `main` | 自动发布 |
| Actions 页面 Run workflow | 手动发布 |

流程：Temurin JDK 8 + `mvn -B clean package -DskipTests` → `sshpass + scp` 传 jar
（先落 `.uploading`，比对大小一致才改名 `.jar.new`）、`remote.sh`、`server.env`
→ 远端 `remote.sh restart`（停旧 → 换 jar → `setsid` 启动）→ 轮询 `http://<host>:<port>/` 探活。

部署目录 / jar 名 / 端口全部从入库的 `sh/server.env` 解析，CI 里不另存一份配置。

### 需要的仓库 Secrets（Settings → Secrets and variables → Actions）

| Secret | 值 |
|---|---|
| `SSH_HOST` | 服务器 IP |
| `SSH_USER` | 登录账号 |
| `SSH_PASSWORD` | 登录口令（与本地 `deploy.env` 的 `PWD` 同一份） |
| `SSH_KNOWN_HOSTS` | 服务器主机公钥，`ssh-keyscan -t ed25519 <IP>` 输出整行 |
| `SSH_PORT` | 可选，默认 22 |

> 不需要 `APP_ENV`。v1.7.3 起密钥只放服务器部署目录的 `app.env`，由 `remote.sh` 启动前逐行 `export`，
> 构建产物里不含任何凭据 —— 所以 CI 打出来的包和本地打出来的完全一致。

## 二、哪些文件入库

| 文件 | 作用 | 入库 |
|---|---|---|
| `remote.sh` | 远端执行逻辑（停旧 → 换 jar → 启动 → 探活） | ✅ |
| `server.env` | 部署目录 / 远端 JDK / JVM 参数 / 启动参数 | ✅ |
| `server-fix-github-dns.sh` | 服务器上一次性的 DNS 修复脚本 | ✅ |
| `deploy.bat` / `deploy.env` / `deploy.env.example` | 本机 Windows 快速发布入口与连接凭据 | ❌ |
| `plink.exe` / `pscp.exe` | 命令行 SSH / SCP | ❌ |

应用密钥另算：`shadow-flow-biz/src/main/resources/app.env` 是本机开发用的，
服务器上那份在部署目录（`/home/stock-backtesting/app.env`，`chmod 600`），两份都不入库。

## 三、本地快速发布（仅 agent 用）

不想等 CI 的场合（改一行想立刻看效果），按 `deploy.bat` 的等价三步手打。凭据从 `sh/deploy.env` 读
（`set "SSH=..." ` / `set "PWD=..."` / `set "HOSTKEY=..."`）：

```bash
# 1) 构建（JDK 8）
JAVA_HOME="C:/workspace/java/jdk8x64" /c/workspace/java/apache-maven-3.8.1/bin/mvn -B clean package -DskipTests

# 2) 上传：jar 先落 .jar.new，再传 remote.sh / server.env
sh/pscp.exe -batch -hostkey "$HOSTKEY" -pw "$PWD_" shadow-flow-biz/target/shadow-flow-biz.jar "root@<IP>:/home/stock-backtesting/shadow-flow-biz.jar.new"
sh/pscp.exe -batch -hostkey "$HOSTKEY" -pw "$PWD_" sh/remote.sh "root@<IP>:/home/stock-backtesting/remote.sh"
sh/pscp.exe -batch -hostkey "$HOSTKEY" -pw "$PWD_" sh/server.env "root@<IP>:/home/stock-backtesting/server.env"

# 3) 远端重启（tr -d '\r' 先洗掉 CR，再喂给 bash）
sh/plink.exe -batch -hostkey "$HOSTKEY" -pw "$PWD_" "root@<IP>" "cd /home/stock-backtesting && tr -d '\r' < remote.sh | REMOTE_DIR=/home/stock-backtesting bash -s -- restart"
```

> `deploy.bat` 现在跑不通，别再试：它靠 `call "%HERE%deploy.env"` 加载配置，而 cmd 的 `call`
> 只认 `.bat` / `.cmd`，`.env` 后缀会被静默跳过 —— 变量全空，脚本停在「配置缺项」。
> 真要恢复一键发布，改成先 `copy` 成临时 `.bat` 再 `call`。

## 四、想改什么，改哪个文件

| 想改的东西 | 改哪 |
|---|---|
| 应用凭据（数据库口令 / 超管口令 / 行情令牌 / 钉钉机器人 / 发信授权码） | 服务器部署目录的 `app.env`（本机开发改 `src/main/resources/app.env`） |
| 部署目录、远端 JDK 路径 | `server.env` 的 `REMOTE_DIR` / `JAVA` |
| 应用端口、启动参数（含各类开关） | `server.env` 的 `ARGS` |
| JVM 内存 / GC | `server.env` 的 `OPTS` |
| 发布流程本身 | `.github/workflows/deploy.yml` 与 `remote.sh` |

> ⚠️ `ARGS` 里的开关一个都不能少。yml 里这些开关默认 `false`，配置表不回写 `enabled`，
> 线上全靠 `server.env` 的 `ARGS` 显式打开。少一个，服务照常运行、功能静默失效 ——
> 例如少了 `--shadowflow.notify.enabled=true`，钉钉告警、关键时点快报、注册通知一条都发不出去。

## 五、回滚

部署目录里常留两份：`shadow-flow-biz.jar` 与 `shadow-flow-biz.jar.bak`（`remote.sh` 每次发布自动滚动）。
回滚就是把备份换回正式名再重启：

```bash
cd /home/stock-backtesting
cp shadow-flow-biz.jar.bak shadow-flow-biz.jar
```

然后随便触发一次发布（CI Run workflow，或本地第 3 步）。只重启不换包的口径是
`bash remote.sh restart` —— 没有 `.jar.new` 它会保留当前包。

## 六、常见问题

- **CI 报 `Permission denied`**：`SSH_PASSWORD` 与服务器口令不一致，或账号不是 `SSH_USER` 指定的那个。
- **CI 报 `Host key verification failed`**：`SSH_KNOWN_HOSTS` 过期（重装 / 换 IP），重新 `ssh-keyscan` 后更新 Secret。
- **服务起不来**：`remote.sh` 会打印最近 30 行日志；最常见是部署目录缺 `app.env` 或里面的占位文字没换真值。
- **`remote.sh` 报 `set: -: invalid option`**：脚本被存成了 CRLF。CI 与本地发布都会先 `tr -d '\r'`，
  服务器上手跑时也要加这一步：`tr -d '\r' < remote.sh > /tmp/remote_lf.sh`。
